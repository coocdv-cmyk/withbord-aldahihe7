# 03 — محرّك التشغيل والأنيميشن في VideoScribe 1.21.0
### تفكيك هندسي كامل لطبقة العرض: PixiJS 8 + React 19 + GSAP

> **الهدف:** فهم كيف يتحرك كل عنصر على الشاشة في VideoScribe، وكيف يُبنى المسرح (Stage)، وكيف يتحكّم الزمن بكل شيء — تمهيدًا لبناء محرّك عرض ومنافس أقوى (عربي أولًا).
>
> **المصدر:** الكود الأصلي TypeScript المسترجَع من source maps داخل `app.asar`.
> **الاصطلاح:** كل الإسنادات في هذا الملف نسبية إلى `vs-analysis/recovered/src/js/`، بالشكل `مسار/ملف.ts:رقم السطر`. لم يُعدَّل أي ملف في `recovered/src`.

## 0. ملخّص تنفيذي

محرّك التشغيل في VideoScribe 1.21.0 مبنيّ على مزيج غير شائع:

| المكوّن | الدور |
|---|---|
| **PixiJS 8** WebGL | الرسم الفعلي (sprites، graphics، text، masks، filters) |
| **@pixi/react** (react-reconciler) | بناء شجرة العرض تصريحيًا داخل React |
| **GSAP** | كل حركة على الشاشة + الـ ticker المركزي (بديل `requestAnimationFrame` الموحّد) |
| **GSAP PixiPlugin** | الجسر بين خصائص GSAP وخصائص كائنات Pixi (`pixi: { x, y, alpha, scale, rotation }`) |
| **pixi-viewport** | «الكاميرا» الفعلية: zoom + pan على مسرح واسع (3× أبعاد الكانفس في كل اتجاه) |
| **Howler** (sprites) | الصوت، بمزامنة يدوية عبر `setTimeout` مع زمن الـ timeline |
| **Web Worker + msdf-atlas-gen WASM** | توليد bitmap fonts (MSDF) عند الطلب لكل مجموعة محارف مستخدمة فعليًا |
| **gsap.ticker** | محرّك الوقت الوحيد: كل شيء (تقدّم الزمن، الرسم، فحص الحضور) يمرّ من خلاله |

النموذج الزمني **مركزي واحد**: `gsap.timeline` واحدة باسم `main-timeline` (`editor/PlayerContext/index.tsx:157`) تُضاف إليها timeline لكل مشهد، وداخلها timeline لكل عنصر، وداخلها tweens تُحرّك خصائص كائنات Pixi مباشرة. لا يوجد ticker خاص بـ Pixi: الـ render يُستدعى من `gsap.ticker` (`playback/pixi-player/components/PixiPlayer.tsx:59`)، و`autoStart={false}` و`sharedTicker={false}` يمنعان Pixi من تشغيل حلقة خاصة (`PixiPlayer.tsx:117-118`).

## 1. المعمارية: بناء مسرح Pixi داخل React

### 1.1 شجرة المكوّنات الكاملة

```
PlaybackLoader (Redux: playbackScribe)
└─ PlaybackView (class component — يتصل بـ PlayerContext عبر contextType)
   ├─ PixiPlayer                      ← الجذر البصري
   │  └─ PlaybackProjectProvider      ← يوفّر ExistingScribeModel
   │     └─ SceneTimingsProvider      ← خريطة توقيتات كل المشاهد (start/length)
   │        └─ <Application>          ← @pixi/react: PixiJS Application
   │           ├─ SceneProvider[scene0] → Scene
   │           ├─ SceneProvider[scene1] → Scene
   │           ├─ …
   │           ├─ ProjectWatermark
   │           └─ BrandKitLogoOverlay
   └─ PlaybackChrome (أزرار التشغيل/الصوت/الملء/الشريط الزمني)
```

(`playback/PlaybackView.tsx:178-195`، `playback/pixi-player/components/PixiPlayer.tsx:106-133`)

كل مشهد في المشروع يُركَّب مرة واحدة دفعةً واحدة (كل `Scene` موجودة في الشجرة من البداية)، والظهور/الإخفاء يقع عبر `visible` لا عبر mount/unmount — قرار مهم للأداء وللـ seek العشوائي.

داخل `Scene` (`playback/pixi-player/components/Scene.tsx:121-179`):

```
CursorLayerProvider
├─ SceneTransitionContainer          ← انتقال الدخول (fade/slide/bounce/drag-on/erase)
│  └─ SceneTransitionExitContainer   ← انتقال الخروج إلى المشهد التالي (slide فقط حاليًا)
│     └─ pixiContainer "Scene container" (visible حسب الزمن)
│        ├─ pixiGraphics  "Scene background color"
│        └─ CameraViewport (pixi-viewport)
│           └─ عنصر × N:
│              CurrentCameraProvider → CurrentElementProvider → ElementComponent
└─ CursorLayer                       ← طبقة المؤشرات فوق كل شيء داخل المشهد
```

### 1.2 الطبقات (Layers)

ترتيب الرسم النهائي على الـ Stage:

1. **خلفية المشهد** — `Graphics.rect(...).fill(scene.settings.backgroundColor)` (`Scene.tsx:112-119`).
2. **عناصر المشهد** — داخل `CameraViewport` (عالم Pixi: عناصر بأبعادها الأصلية، والـ viewport يتولّى التحويل).
3. **طبقة المؤشر** — `CursorLayer` (`Scene.tsx:177`). المؤشرات **تُنزع من شجرة React وتُضاف يدويًا** إلى هذه الطبقة عبر `addChild` (`Cursor.tsx:122-124`)، لذا هي دائمًا فوق كل العناصر مهما كان ترتيبها — وهي تقنية «layer» يدوية داخل reconciler.
4. **العلامة المائية للمشروع** — `ProjectWatermark` على مستوى الجذر (`PixiPlayer.tsx:128`)، أي فوق كل المشاهد.
5. **شعار Brand Kit** — `BrandKitLogoOverlay` آخر عنصر (`PixiPlayer.tsx:129`)، أي أعلى طبقة.

أما انتقالات المشهد (Dاخلة/خارجة) فهي **مغلّفات حاويات** حول المشهد كله، بما في ذلك طبقة المؤشر — لأن `CursorLayer` تقع داخل `SceneTransitionContainer` (`Scene.tsx:123-177`).

### 1.3 الكاميرا كـ Viewport وليس كـ Container

الكاميرا ليست تحويلًا يدويًا على الحاوية، بل كائن `pixi-viewport` (المكوّن `CameraViewport`) بأبعاد شاشة = أبعاد الكانفس، وعالم = 3× الأبعاد في كل اتجاه (`getCanvasObjectCoordinates` في `editor/EditorCanvas/helpers/getCanvasDimensions.tsx:4-14`). التحريك يتم بـ `viewport.moveCorner(x, y)` + `viewport.setZoom(scale)` (`Animations/CameraViewport.tsx:58-59,93-96`). التفاصيل في §6.

### 1.4 إدارة الحالة عبر Contexts

سبعة contexts متداخلة، كل واحد مسؤول عن بُعد واحد:

| Context | الملف | ما يوفّره |
|---|---|---|
| `PlayerContext` | `editor/PlayerContext/index.tsx:137` | الـ timeline الرئيسية + play/pause/seek/stop + سجل الجاهزية + `seekAndRender` |
| `AudioPlayerContext` | `editor/PlayerContext/AudioPlayerContext.tsx:27` | تحميل الصوت، play(timeMs)، mute/volume |
| `PlaybackProjectContext` | `pixi-player/components/PlaybackProjectContext.tsx` | المشروع المُطبَّع للعرض |
| `SceneTimingsProvider` | `editor/Timeline/AdvancedTimeline/contexts/SceneTiming.tsx` | `getSceneStartEndTimes` لكل مشهد |
| `SceneContext` (لكل مشهد) | `pixi-player/components/SceneContext.tsx` | بداية/مدة المشهد، انتقال المشهد التالي، `maxTextResolution` |
| `CurrentCameraProvider` | `pixi-player/components/CurrentCameraContext.tsx` | الكاميرا السارية للعنصر + `cameraBounds` |
| `CurrentElementProvider` | `pixi-player/components/CurrentElementContext.tsx` | العنصر الحالي + `elementBounds` (AABB مع الدوران) + `animationAbsoluteStartTime` |
| `CursorLayerContext` | `pixi-player/components/CursorLayerContext.tsx` | مرجع طبقة المؤشر |

ملاحظة لافتة: الـ contexts ثابتة القيمة تقريبًا (تُحسب بـ `useMemo` من بيانات المشروع)، والتغيّر الحيّ (زمن، موضع، شفافية) **لا يمرّ عبر React** أبدًا، بل عبر تلاعب مباشر بكائنات Pixi داخل `onUpdate` callbacks الخاصة بـ GSAP. هذا هو المفتاح المعماري: **React يبني الشجرة مرة واحدة، وGSAP يحرّكها 60 مرة/ثانية بلا re-render**.

### 1.5 دورة الحياة: من التركيب إلى التشغيل

1. **البناء:** `Scene` تنتظر `useApplication().isInitialised` قبل أن تُرسم (`Scene.tsx:122`).
2. **تسجيل جاهزية العناصر:** كل عنصر افتراضي/نصي/شكلي يبني كل tweens الخاصة به ثم ينادي `registry.updateReadyState(element.id, true)` (مثال: `RasterImageElement.tsx:103-107`). السجل مُعبَّأ مسبقًا من `getInitialElementRegistrations` بكل العناصر والمشاهد (`pixi-player/helpers/getInitialElementRegistrations.ts:13-41`) لتجنّب سباق "جاهز قبل التسجيل".
3. **الانتقالات:** `Scene` لا تُعلَن جاهزة إلا بعد اكتمال بناء انتقال الدخول **والخروج** معًا (`Scene.tsx:96-110`).
4. **التسلسل الحاسم:** عندما يصبح `visualPlayerIsReady && audioLoaded && allElementsReady` (إن لزم) → `dispatch(playbackIsReadyAction())` ثم `play()` تلقائيًا إن كان `autoPlay` (`editor/PlayerContext/index.tsx:585-596`).
5. **النهاية:** `onComplete` للـ main timeline → `endPlayback()` → إن كان `resetAtCompletion` يُفرَّغ كل شيء ويُغلق العرض، وإلا pause + seek(0) (`index.tsx:510-529, 572-577`).
6. **الاستئناف بمنتصف التشغيل:** كل المكوّنات تحسب `initialProgress` من `mainTimeline.time()` عند البناء وتهيّئ حالة الرسوم عليها (مثال ممتاز: `MaskRevealable.tsx:62-77`، و`CameraViewport.tsx:46-59`). هذه نقطة قوة حقيقية: الانتقال لمشهد وسط المشروع لا "يُقرأ" المشهد من الصفر.

### 1.6 وضع الرندر (Renderer mode / التصدير)

نفس المكوّنات تُستخدم للتصدير على السحابة:
- `RendererCapture` ينتظر `visualPlayerIsReady` و`elementsBeforeRenderStartReady` ثم يدور على الزمن بمعدل 25 إطارًا/ثانية (`defaults.ts:12-14`) ويستدعي `seekAndRender(time)` لكل إطار (`renderer/RendererCapture.tsx:29-62`).
- `seekAndRender` يقفز بالـ timeline، ينفّذ `gsap.ticker.tick()` لدفع حالة كل tweens فورًا، ثم يُصدّر الكانفس بـ `renderer.extract.canvas({target: app.stage})` → `toBlob('image/png')` (`editor/PlayerContext/index.tsx:363-432`). يوجد تحذير صريح في الكود من سباق `app.render()` + `readPixels` المزدوج الذي يُسقط GPU.
- قبل التصدير تُجرَّد بقية المشروع من العناصر غير المطلوبة (`transformProjectForRendering`) وتُولَّد bitmap fonts لكل النصوص (`sagas/playbackSagas.js:54-63`).
- المؤشر يُحوَّل إلى موضعه المحسوب *في زمن الإطار* لا موضعه اللحظي، لأن كل شيء داخل onUpdate الخاصة بكل tween — وهذا سبب رئيسي لكون الفrames الخارجة ثابتة (deterministic) بقدر مقبول.

## 2. نموذج الزمن (Time Model)

### 2.1 حسابات المدد — كل شيء بالميلي ثانية ثم يُحوَّل للثواني

القواعد الأساسية في `playback/helpers/timings.ts`:

- مدة العنصر = `entrance + emphasis + exit + pause` (`timings.ts:77-84`). كل مرحلة تُقرأ بترتيب أولوية: العنصر نفسه ← إعدادات المشهد ← إعدادات المشروع ← 0 (`timings.ts:100-125`).
- طول المشهد = `max(طول الصوت، Σ مدد العناصر + sceneTransitionTime)` (`timings.ts:184-198`). **الصوت يستطيع تمديد المشهد**.
- بداية المشهد = Σ أطوال المشاهد السابقة (بالنفس القاعدة) (`timings.ts:162-182`).
- بداية العنصر داخل المشروع = بداية المشهد + `sceneTransitionTime` + Σ مدد العناصر السابقة (`timings.ts:127-160`).
- الطول الكلي = `endTime` لآخر مشهد (`playback/helpers/getScribeLengthMs.ts:4-14`).
- حالة خاصة: كاميرا البداية `entrance=0` دائمًا (`timings.ts:11-14`)، والكاميرا لا emphasis لها (`timings.ts:33-37`) ولا exit (`timings.ts:20-31`).

يُخزَّن في Redux، لكن يظهر `SceneTimingsProvider` في الـ React tree يُحسب مرة على `project` (`SceneTiming.tsx:23-32`). وفي المحرّر توجد دالة موازية `getElementTimings` تستخدم نفس الدوال مع بداية المشهد كإزاحة (`playback/helpers/getElementTimings.ts:21-30`).

### 2.2 شجرة GSAP: timeline واحدة تحكم الكون

```
main-timeline (paused, id='main-timeline')        ← editor/PlayerContext/index.tsx:157
 │  .to({}, {duration: totalProjectLengthMs})     ← "حشو" يحدّد الطول لشريط التقدّم
 ├─ at sceneStartTime → scene-timeline-<id>       ← Scene.tsx:88 (mainTimline.add(sceneTimeline.play(), startTime))
 │    .to({}, {duration: sceneDuration})  ← حشو بطول المشهد + انتقال المشهد التالي (Scene.tsx:76-77)
 │    ├─ scene transition tweens (عند 0)
 │    ├─ scene exit transition (عند duration المشهد)
 │    ├─ camera tweens (CameraViewport.tsx:86-100)
 │    └─ عنصر → <element>-timeline-<id>  (تضاف في موضعها المطلق)
 │         ├─ visibility-timeline  (VisibilityManager)
 │         ├─ entrance tween(s)     (DrawIn/Erase/Move/DragIn/Fade/BounceIn)
 │         ├─ emphasis tween(s)     (Pulse/Spin/Shake/Bounce loops)
 │         ├─ exit tween(s)         (Fade/Move/Erase)
 │         └─ pause dummy tween     ← `.to({}, {duration: pauseDuration}, pauseRelativeStartTime)`
 └─ …
```

مثال التوقيت الأساسي الذي تكرره كل مكوّنات العناصر (هنا النص، `StaticTextElement.tsx:51-57`):

```ts
const animationAbsoluteStartTime = toSeconds(getStartTime(project, element.id));
const entranceAnimationRelativeStartTime = 0;
const emphasisAnimationRelativeStartTime = entranceAnimationRelativeStartTime + entranceAnimationDuration;
const exitAnimationRelativeStartTime = emphasisAnimationRelativeStartTime + (element.emphasisAnimationTime ?? 0);
const pauseRelativeStartTime = exitAnimationRelativeStartTime + (element.exitAnimationTime ?? 0);
```

ثم `mainTimeline.add(elementTimeline.play(), animationAbsoluteStartTime)` — أي أن **مدة الـ pause ليست حركة، بل مساحة زمنية فارغة** ("dummy tween") تُبعد بداية العنصر التالي. العنصر نفسه لا "ينتظر" الـ pause: هو يبقى ظاهرًا بلا تغيير.

### 2.3 كيف يتقدّم الزمن فعليًا؟

- **لا `requestAnimationFrame` خاص، ولا ticker من Pixi:** `gsap.ticker.add(renderLoop)` يستدعي `app.render()` في كل إطار (`PixiPlayer.tsx:43-63`). أي أن GSAP هو حلقة اللعبة.
- الـ tween الرئيسي `paused: true`، ويُشغَّل بـ `mainTimelineRef.current.play()` (`index.tsx:471`).
- عند `playbackState !== 'idle'` يُضاف `checkAndInterrupt` إلى الـ ticker لفحص الجاهزية في كل إطار (`index.tsx:548-560`).
- `onUpdate` للـ main timeline يحوّل الزمن إلى ms ويوزّعه على كل المشتركين (أساسًا `Scrubber`) (`index.tsx:562-583`).

### 2.4 التمرير (Scrub) والقفز

`seek(progress)` = `timeline.time((progress/100) * totalProjectLengthMs)` (`index.tsx:495-501`). سلسلة السحب في `Scrubber`:
- `onScrubStart → seekStart()` يوقف مؤقتًا ويسجّل هل كان يعمل (`index.tsx:489-493`).
- الحركة = `pointermove` على مستوى `window` وتحويل المسافة لنسبة من عرض الشريط (`Scrubber.tsx:95-101`).
- `onScrubEnd → seekEnd()` يعيد التشغيل إن كان يعمل (`index.tsx:503-508`).
- لوحة المفاتيح: أسهم = خطوة 0.1%، مع Shift/Meta = 1% (`Scrubber.tsx:108-122`).

القفز المباشر يعمل لأن كل الحالات الحرجة تُشتق من `timeline.time()`: `VisibilityManager.onReverseComplete` يعيد الحضور الصحيح (`VisibilityManager.tsx:75-79`)، و`MaskRevealable`/`SceneTransitionErase` يعيدان بناء القناع من الـ progress الحالي (`MaskRevealable.tsx:62-77`، `SceneTransitionErase.tsx:52-62`)، والتخطيطات المبنية على `onStart` فقط قد تُفوَّت لكن يغطيها فحص `initialProgress`.

### 2.5 التزامن مع الصوت (Howler)

- التحميل: كل مشروع → `loadProjectAudios` ثم لكل `assetId` واحد `Howl` يحوي **sprite sheet**: مقطع لكل clip بإزاحة `startOffset*1000` ومدة `instanceDuration*1000` (`editor/PlayerContext/loadAudioIntoSprites.ts:31-42`). `Howl` واحد لكل ملف صوتي مع عدة sprites = ذاكرة أقل وعدد أقل من الـ decoders.
- عند `play(timeMs)`: يُقسَّم الصوت إلى (أ) مقاطع «جارية الآن» تُشغَّل فورًا مع `howl.seek(...)` للوصول للموضع الصحيح، و(ب) مقاطع «لم تبدأ» تُجدول بـ `setTimeout` (`AudioPlayerContext.tsx:107-191`). Fade-out يُحسب رياضيًا: إن كان قد بدأ يُطبَّق جزئيًا، وإلا يُجدول.
- الفروق الدقيقة: fade-out يتجاهل إزاحة الـ sprite في `seek` (تعليق صريح في الكود `AudioPlayerContext.tsx:134`)، والإيقاف يمسح كل المؤقتات و`stop()` لكل الأصوات (`:80-93`).
- عند الـ buffering: `audioPlayerContext.stop()` ثم عند الاستئناف `audioPlayerContext.play(toMilliseconds(mainTimeline.time()))` — أي **إعادة مزامنة كاملة** بدلًا من إيقاف/تشغيل الصوت (`index.tsx:444-463`).

### 2.6 الجاهزية والـ buffering (سجل العناصر)

- `RegisteredElement = {id, startTime, isReady}` (`index.tsx:131-135`).
- `checkAndInterrupt` يعمل على كل إطار: إن وُجد عنصر غير جاهز يبدأ قريبًا (`startTime <= time + 5s`، الثابت `INTERRUPT_THRESHOLD_SECONDS = 5` في `index.tsx:53,308-318`) → يوقف الـ timeline والصوت ويلبس حالة `buffering`، ثم يستأنف تلقائيًا عند الجاهزية (`index.tsx:444-463`).
- في وضع الرندر تُستخدم `waitForElementsReadyAt` التي تعيد الفحص بـ `requestAnimationFrame` حتى تجهز العناصر (`index.tsx:337-353`).

## 3. كتالوج الأنيميشنات الكامل

كل الأنيميشنات تُكتب كـ tweens على خصائص **كائنات Pixi مباشرة** عبر `PixiPlugin` (مُسجَّل في `PixiPlayer.tsx:27-28`). البنية الموحّدة لكل مكوّن: مكوّن حاوية + `useGSAP` يبني timeline فرعية `paused` تُضاف إلى timeline العنصر عبر `timeline.add(child.play(), startTime)`، ثم `onReady()`.

### 3.2 Entrance: كيف يُختار الأنيميشن

`EntranceAnimationContainer` هو الموزّع (`Animations/EntranceAnimationContainer.tsx:29-92`):
- النوع من `element.entranceAnimation?.id ?? element.entranceTween?.id ?? 'hand-draw'` — أي أن العُنصر القديم بلا تويين صريح يُعامل كـ hand-draw.
- إن كانت المدة 0 → يُعاد الأبناء كما هم بلا غلاف.
- الأنواع: `fade-in` → Fade؛ `move-in` → Move باتجاه `entranceTween.tweens[0].position ?? '@l'`؛ `bounce-in` → BounceIn؛ `drag-in` → DragIn؛ و`ENTRANCE_ANIMATION_THAT_HAVE_DRAW_TYPE = [hand-draw, pen-draw, draw]` → DrawIn.
- اختيار الصور/النصوص للـ Split أو Static يقع في `SVGElement.tsx:9-21` و`TextElement.tsx:10-23`: لو كان نوع الدخول «رسميًا» → Split (رسم تدريجي حقيقي)، وإلا Static (رسم كامل + ربما Move/Fade).

### 3.3 DrawIn بعمق

`DrawIn` لا يرسم شيئًا جديدًا: يضع عنصرًا مرسومًا كاملًا ويقنعه بقناع يُرسم تدريجيًا. التفاصيل المهمة:

1. مسار القناع = «scribble» خطوط أفقية/عمودية متعرجة تغطي المستطيل كله، تُولَّد بـ `generateScribblePathArray(width, height)` (`playback/helpers/generateScribblePathArray.ts:8-93`)، بتردد 20 خطًا وحلّ `SCRIBBLE_RESOLUTION=40` وتكبير 10% لتجنّب حواف غير مكتملة.
2. القناع يُرسم بـ `drawScribbleMask` كـ stroke بسماكة `stepSize` (`pixi-player/helpers/drawScribbleMask.ts:13-22`).
3. حالة الـ mask: عند progress 0 أو 1 يُلغى القناع تمامًا (`container.mask = null`) — لذا لا يوجد أي overhead في الحالتين الطرفيتين (وهذه نقطة أداء→§9).
4. المؤشر: مؤقّت مستقل بنفس المدة يقف على آخر نقطة مرسومة (`scribbleArray[drawTo-1]`) ويحوّلها من إحداثيات محلية → عالم → شاشة عبر transform العنصر والكاميرا (`DrawIn.tsx:129-145`).

### 3.4 Erase بعمق

نفس الفكرة لكن على الخروج (`exit-erase`، `ExitAnimationContainer.tsx:71-77`). `generateScribblePathArray` يُبنى من `elementBounds` (AABB مع الدوران) لا من أبعاد العنصر الخام (`Erase.tsx:33-36`)، والقناع يُضبط `inverse: true` عند البدء (`Erase.tsx:49-55`) بينما داخل `onUpdate` يُسنَد `container.mask = mask` مباشرة (`Erase.tsx:63`). هذه نقطة تستحق التحقق عند إعادة التنفيذ: الفرق بين `setMask({inverse})` و`mask=` في Pixi 8 هو الفرق بين «إخفاء ما تحت القناع» و«إظهار ما تحت القناع فقط»، والسلوك المرئي المألوف في VideoScribe هو الاختفاء التدريجي حيث مرّ القناع.

### 3.5 MaskRevealable (الرسم في SVG بمسارات حقيقية)

هذا أهم مكوّن للرسم الجيد:
- يتلقى `drawCommands`: قائمة strokes، كل stroke فيه نقاط مع `pathLength` وبيانات bezier اختيارية (`assets/svg-loader.ts:21-25`).
- يحوّل الزمن إلى **طول مرسوم**: `drawToLength = (frame/frames)*totalLength` ثم `drawCommandsUpToLength` (في `helpers/generateGraphicsContextFromDrawCommands.ts:120-126`) تتعامل مع cubic/quadratic بقطع منحنى Bezier (`bezier.split`) عند النسبة المطلوبة (`:59-100`).
- عند `onStart` يُبنى القناع من الصفر، وعند `progress===1` يُلغى القناع والرسم كامل.
- ملفوف بـ `FXAAFilter` لتلطيف حواف القناع (`MaskRevealable.tsx:140`)—التفصيل في §9.
- يحتوي أيضًا على مزامنة ذكية عند الالتحاق بمنتصف الحركة: `gsap.parseEase('power1.out')` لحساب الإطار الحالي، رغم أن الحركة نفسها خطية. أي أن الالتحاق بمنتصف الحركة يرسم أكثر مما يجب قليلًا (تعويض بصري محتمل).

كيف تُبنى الـ drawCommands لصورة SVG؟ (`assets/svg-loader.ts`):
1. تُفكَّك SVG إلى أجزاء عبر معرّفات مخصصة: `#vs-meta` / `#vs-reveal path` / `#vs-outline path` / `#vs-colour` (`playback/helpers/svgSplitter.ts:8-23`).
2. إن وُجدت `revealPaths` (منظّفة من صانع الأصول) تُستخدم مباشرة.
3. وإلا (صور vectorized أو fills بلا مسارات كشف) تُولَّد مسارات بديلة: محاولة «skeleton» عصبية (`generatePathFromSkeletons`)، ثم fallback إلى `generateScribbleFromHull` (تحدّب من حدود البكسل)، ثم أخيرًا scribble مستطيل بتردد 10 (`generateFallbackRevealPath.ts:28-52`).
4. النتيجة تُخزَّن في IndexedDB وتُقرأ لاحقًا حسب مفتاح يشمل `assetId + recolor + viewbox` (`svg-loader.ts:189-259`).

### 3.6 Emphasis (الحركات الدورية)

كلها تشترك في:
- `loops = element.emphasisAnimationLoops || 1` وقسمة المدة على عدد الـ loops.
- تحضير pivot = **المركز المرئي بعد scale+rotation+translate** عبر `calculateElementPivot` ثم `container.pivot.set + position.set` (`hooks/useEmphasisAnimation.ts:18-24`, `pixi-player/helpers/calculateElementPivot.ts:20-41`). بدون هذا كان الـ scale/rotation سيتم حول (0,0).
- تعويض الكاميرا: مسافات Bounce/Shake تُقسم على `camera.scale`، وPulse يستخدم `1 + 0.1/camera.scale` (`Bounce.tsx:38`، `Shake.tsx:37-39`، `Pulse.tsx:33`) — فالحركة تبدو **مطلقة على الشاشة** مهما كانت الكاميرا مكبّرة.
- الألوان/القيم الافتراضية موثقة في `config/tweens.ts` (pulse: 1.1 ثم 1، shake: ±80، bounce: ∓80، spin: ±360).

### 3.7 Scene Transitions

- **الدخول** (`SceneTransitionContainer.tsx:26-105`): `fade` → Fade؛ `slide`/`bounce` → SceneTransitionMove بفرق الـ ease فقط؛ `drag-on` → SceneTransitionDrag؛ `erase` → SceneTransitionErase.
- **الخروج** (`SceneTransitionExitContainer.tsx:22-51`): حاليًا **slide فقط**: إذا كان المشهد التالي انتقاله slide، فإن المشهد الحالي ينزلق خارج الشاشة بمدة `nextSceneTransitionTime` بدءًا من `exitingSceneDuration`، والاتجاه يُقرأ من إعداد المشهد التالي (الافتراضي `@t`). هذا هو تلميح الكود الواضح بأن النظام قابل للتوسّع لأنواع خروج أكثر.
- مسافات البداية لكل اتجاه (بعرض/ارتفاع الشاشة الكامل) في `getSceneMoveTransitionsStartPosition.tsx:7-26`.
- `SceneTransitionDrag` يستخدم **70% للحركة و30% لخروج اليد** (`SceneTransitionDrag.tsx:22,43-44`) — ونفس النسبة مستخدمة في DragIn للعنصر.

### 3.8 GIF و الحركة المستقلة

`GifSprite` مع `autoPlay={false}`، والحركة تُدار يدويًا من timeline خطية تنطلق **بعد انتهاء الدخول**: `animationAbsoluteStartTime + emphasisAnimationRelativeStartTime` (`GIFImageElement.tsx:142-143`). الإطار يُختار بمقارنة زمن الحلقة مع `frame.start/end`، ومدة العرض تُحدَّد بـ: إن كان للعنصر خروج → مدة الـ emphasis+exit، وإلا → حتى نهاية انتقال المشهد التالي (`GIFImageElement.tsx:62-69`).

## 4. اليد/المؤشر (Cursor)

### 4.1 التمثيل

- المؤشر **ليس** صورة ثابتة لعنصر، بل `AnimatedSprite` بإطارين: `textures=[cursor1Texture, cursor2Texture]` (`Cursor.tsx:143-146`)، تُحمَّل من موارد المخزن عبر `getCursorResourcesAndMetadata(cursors, cursorId)` (`Cursor.tsx:65-68`)؛ وجود مورد ثانٍ = يد متحركة.
- الموضع الابتدائي `x=Infinity, y=Infinity` (أي خارج أي شيء) والحاوية `visible={false}` من الأب حتى يبدأ الأنيميشن (`Cursor.tsx:144`).
- **إزاحة اليد**: `xOffset/yOffset = (handOffsetX/Y - 100) * spriteScale`، والثابت `CURSOR_OFFSET_MAGIC_NUMBER = 100` موثّق في الكود كأثر تاريخي من VideoScribe القديم (`cursorSpriteOffsets.ts:1-9`).
- **مقياس اليد**: 1.5 في landscape/square و2 في portrait «لمواجهة صغر صور اليد» (`cursorSpriteOffsets.ts:16-20`).

### 4.2 الحركة

- المؤشر لا يملك timeline خاصة له في أغلب الحالات: موضعه **يُحدَّث في `onUpdate`** الخاصة بأنيميشن العنصر من نقاط محسوبة مسبقًا:
  - DrawIn/Erase: آخر نقطة من `scribbleArray` (`DrawIn.tsx:129-145`).
  - SplitSVGElement: `generateCursorPoints(drawCommands, duration)` — عيّنة لكل إطار 60fps من نقطة النهاية عند كل نسبة، مع تحويل كامل (flip → scale → rotate → translate → camera) (`SplitSVGElement.tsx:188-256`).
  - SplitTextElement: نقاط من مسار قناع المحارف، وموضع على الشاشة عبر `char.toGlobal(new Point(...))` (`SplitTextElement.tsx:165-182`).
- **أنيميشن اليد**: `animateHand(direction)` تنادي `sprite.gotoAndStop(1)` لليسار و`gotoAndStop(0)` لليمين (`Cursor.tsx:36-47`)، ويُستدعى بناء على مقارنة `lastFrameX` مع الموضع الجديد — أي اليد «تنقلب» حسب اتجاه الحركة الأفقية.
- كل المؤشرات تنتهي بمواضع الحواف: `visible=false` عند progress 0 أو 1، وإلا true — النمط مكرّر حرفيًا في كل مكوّنات المؤشر.

### 4.3 الأنواع وكيف تُختار

| النوع | من يختاره | الاستخدام |
|---|---|---|
| `handDraw` | أي نوع دخول رسمي ليس pen-draw (`DrawIn.tsx:198`، `SplitTextElement.tsx:61`، `SplitSVGElement.tsx:85`) | الرسم اليدوي |
| `penDraw` | `entranceAnimation.id === 'pen-draw'` | الرسم بقلم |

## 5. الكاميرا

### 5.1 التمثيل

عنصر `Camera` هو عنصر عادي في `scene.elementIds` لكنه لا يُرسم؛ يُفلتر قبل بناء العناصر (`Scene.tsx:59,150-156`)، ويُستخدم لبناء:
- سلسلة كاميرات متتابعة بالمشهد: الأولى = موضع ابتدائي، وكل تالية = «keyframe» انتقالي.
- `cameraBounds` = مستطيل العالم المرئي: `(camera.x, camera.y, viewportW/scale, viewportH/scale)` (`CurrentCameraContext.tsx:21-30`) — يُستخدم لكل حسابات «خارج الشاشة» (move/drag/bounce).

### 5.2 التنفيذ

`CameraViewport` (`Animations/CameraViewport.tsx`):
- إنشاء `pixi-viewport` بعرض/ارتفاع الشاشة وعالم = 3× كانفس في كل اتجاه (`:107-114`)، مع تعطيل التفاعل (لا events للمستخدم).
- عند البناء: يحسب الموضع الحالي من الزمن الحالي بـ `getCameraPositionAtTime` ثم `setZoom` + `moveCorner` (`:46-59`).
- لكل كاميرا i>0: tween على كائن وسيط `{x, y, zoom}` في **فضاء الشاشة** `(camera.x * camera.scale)`، ثم في `onUpdate` يُقسَم على zoom الحالي ليُعطى إحداثيات عالم ويُطبَّق `moveCorner(worldX, worldY)` (`:70-97`). هذه الخدعة تجعل الحركة المستقيمة على الشاشة مستقيمة رغم تغيّر التكبير أثناءها.
- المدة/easing من عنصر الكاميرا (`camera.animationTime`، `camera.easingType`)، والبداية المطلقة = `getStartTime(project, camera.id)` محوَّلة إلى نسبية للمشهد (`:82-84`).
- الكاميرا لا تأخذ emphasis/exit (`timings.ts:20-31, 33-37`) لكن قد تأخذ pause يظهر كـ «توقف الكاميرا»؛ وفي `VisibilityManager` حالة خاصة صريحة: العناصر بلا دخول داخل كاميرا البداية تُعتبر مرئية عندما تصل الكاميرا وتتوقف (`VisibilityManager.tsx:41-49`).

### 5.3 الحساب عند زمن معيّن

`getCameraPositionAtTime` (`helpers/getCameraPositionAtTime.ts:26-108`) يكرّر منطق الأنيميشن لكن في اتجاه عكسي:
- يبحث عن أول كاميرا لم ينتهِ انتقالها، ويتعامل مع `animationDuration===0 || easingType==='no-ease-no-duration'` كقطع فوري (`:67-73`).
- يحسب `easedProgress = parseEase(easingType)(linearProgress)` (افتراضي `power2.out`) ثم يلوّن في فضاء الشاشة ويعود للعالم بالقسمة على `scale` المُلوَّن (`:76-97`).
- هذا يضمن أن بدء التشغيل من منتصف المشروع يعطي كادرًا مطابقًا تمامًا لما سيكون عليه لو لُعب من البداية.

### 5.4 حدود التكبير ودقّة الرسم

- `maxTextResolution` في `SceneContext.tsx:35-40` = `clamp(max(camera.scale), 2)` — أي دقة النص المتجهي ترتفع مع أقصى تكبير في المشهد (بحد أدنى 2).
- حجم تكسشرات SVG يُقيَّد: `getClampedSvgSize(dimension, scale, maxCameraZoom)` ∈ [16, 4096] (`getClampedSvgSize.ts:5-7`, `consts.ts:276-277`, استخدام في `svg-loader.ts:195-198`).
- النص النقطي: دقة الرسملة تُخفَّض إن تجاوزت 4096 بكسل (`StaticTextElement.tsx:59-62`).

## 6. النص (Text)

### 6.1 لماذا bitmap fonts؟

رسم النص المتجهي في Pixi (Text) مكلف جدًا: توليد Texture لكل نص عبر canvas ثم رفعه على GPU، مع تمزّق الحواف عند التكبير. عند التصدير بدقة 1080p+ وبكاميرا مكبّرة، الحل المستخدم هو **MSDF (Multi-channel Signed Distance Field)**:
- حزمة المحارف تُبنى على **قياس المحارف المستخدمة فعليًا** (subset) لكل عائلة خط وأسلوب ووزن (`generateBitmapFonts.ts:58-69`) — ميزة كبيرة للخطوط العربية الكبيرة.
- التوليد في Web Worker: يُحمَّل `msdf-atlas-gen` WASM من CDN، يُفكّ WOFF2 بـ `woff-lib` ثم يُولَّد أطلس PNG + JSON (`BitmapFontWorker/worker.ts:16-22,83-168`)، ويُحوَّل إلى XML bitmap font بأرقام عشرية (بدل تقطيع Pixi لها) عبر `installBitmapFont` (`helpers/installBitmapFont.ts:3-23`).
- النتيجة تُركَّب في Pixi كـ `BitmapFont` وتُخزَّن أسعارها في `Assets.cache` بمفتاح `"<face>-bitmap"` وتُتحقّق تغطية كل محارف النص قبل الاستخدام (`useElementText.ts:70-76`).
- تعويض خلل Pixi المعروف بحذف الأسطر الفارغة في `SplitBitmapText` عبر استبدال السطر الفارغ بمسافة وإضافة Sprite فارغ لتثبيت الارتفاع (`SplitBitmapTextElement.tsx:37-59`) — مع ذكر رقم الـ issue في تعليق الكود.

### 6.2 المسار الكامل لرسم النص

1. `TextElement` يقرر: draw-type → `SplitTextElement` (حرف-بحرف) أو `StaticTextElement` (كامل + دخول آخر) (`TextElement.tsx:10-23`).
2. `useElementText` يجهّز: حجم خط مصغّر بمقياس العنصر، `lineHeight` = `lineHeight * fontSize * SCRIBE_TEXT_MULT` (الثابت التاريخي 1.13 في `defaults.ts:150`)، لون، وأهم شيء **`shouldUseSplitText`** = (نوع الدخول رسمي) أو (أنماط المحارف ليست متطابقة) (`useElementText.ts:22-45`).
3. `areCharacterStylesAllTheSame` يقارن كل الأنماط بشكل مسطّح؛ اختلاف أي لون = يجب أن يكون النص Split لأن التلوين يصير per-character (`helpers/areCharacterStylesAllTheSame.ts:3-15`).
4. التطبيق: `useApplySplitTextCharStyles` يمرّ على الأسطر/المحارف ويطابقها مع `splitText.chars` (المحارف غير البيضاء فقط) ويستبدل `char.style` بلون جديد، ويضبط `char.resolution = maxTextResolution` للنص المتجهي (`hooks/useApplySplitTextCharStyles.ts:20-57`).
5. في الاختيار: bitmap font متاح وكل المحارف مغطاة → `SplitBitmapTextElement`، وإلا → `SplitVectorTextElement` (نصّ متجهي)، وإلا نص عادي (`StaticTextElement.tsx:89-103`).

### 6.3 الرسم حرفًا-بحرف (SplitTextElement)

الآلية Exact:
- `durationPerCharacter = entranceAnimationDuration / splitText.chars.length` (`SplitTextElement.tsx:75`).
- لكل محرف: يُولَّد **مسار قناع** من بكسلات المحرف الملعوبة فعليًا:
  1. يُرسم المحرف في WebGLRenderer بحجم 256×256 ويُستخرج `pixels` (`generateCharacterMaskPath.ts:20-26,66-81`).
  2. `findSeparateImageShapes` يفصل الجزر المنفصلة (مهم للنقاط العربية: نقاط الحروف جزر منفصلة).
  3. `thin` (Zhang-Suen) يرقّق الشكل لهيكل بسماكة 1، وعدد التكرارات = سماكة الفرشاة (`:86-96`).
  4. `generateMaskPath` يولّد مسار الطلاء، ويُخزَّن في **IndexedDB** بمفتاح يصف (bitmap/vector، الخط، الوزن، المحاذاة، الحجم التقريبي، المحرف) مع `Promise` cache في الذاكرة (`:17,35-43,56-59,99`).
- القناع يُطلى بدوائر نصف قطرها `brushSize/2` حتى النسبة الحالية (`generateGraphicsContextFromMaskPathAndBrushData.ts:31-58`)، والمؤشر يقف عند آخر نقطة.
- التوقيت: `textTimeline.add(characterTimeline.play(), charIndex * durationPerCharacter)` — تسلسل تام: كل محرف يبدأ بعد انتهاء سابقه (`SplitTextElement.tsx:188`).

### 6.4 العربية و RTL

هذا الجزء بالغ الأهمية لمنافس عربي:
- `direction(text) === 'rtl'` يفعّل المسار العربي (`useElementText.ts:36`).
- النص يُقطَّع بكلمات عبر `Intl.Segmenter(navigator.language, {granularity:'word'})` ثم يُعالج كل مقطع بـ `ArabicReshaper.convertArabic` (وصل الحروف + الأشكال السياقية) (`:50-57`).
- عند استخدام SplitText (وضع الرسم حرفًا-حرفًا) تُعكس محارف كل سطر فرديًا مع **الحفاظ على ترتيب الأسطر**: `line.split('').reverse().join('')`، والكود يوضّح أن العكس لأن Pixi يرسم من اليسار (`:60-67`). نفس الفكرة مطبقة في `SplitTextElement.tsx:83` عبر `lineChars.toReversed()`.
- في بناء الحزمة يُستخدم النص المُشكّل كثيقة محارف (`generateBitmapFonts.ts:58-62`).
- **قيود يجب ملاحظتها:** لا يوجد معالجة BiDi مختلط RTL/LTR (الأرقام في سياق عربي قد تنعكس)، ولا دعم للتشكيل/kashida، وتصحيح خط الأساس يعتمد على مقارنة «أسطر متعددة» ثابتة.

### 6.5 تصحيح خط الأساس (Baseline Correction)

مشكلة معروفة: Pixi يضع نص MSDF على خط أساس مختلف عن Fabric (المحرّر). الحل في `helpers/fontBaselineCorrections.ts`:
- يُرسم النص نفسه في **Fabric StaticCanvas** (كخلفية صفراء ونص أسود) وفي **Pixi** (بنفس اللون)، ويُقارن أول صفّ فيه بكسل غير الخلفية في الاثنين، والفرق هو التصحيح (`:60-75,175-185`).
- النتيجة تُطبق كـ `y = -correction` على كل مكوّنات النص (`useElementText.ts:133-142` ثم `StaticTextElement.tsx:101`, `SplitVectorTextElement.tsx:26`).
- الكاش بمفتاح `font-lineHeight-fontSize-class` ومخزّن كـ Promise (لا يُحسب مرتين متوازيتين) (`:77-119`).
- رسّام مؤقت مُنفصل يُنشأ ويُدمَّر لكل قياس (`:144-191`) — مكلف لكنه مرة واحدة لكل تركيبة.

## 8. الأداء: أين التكلفة وما هو التخفيف الموجود

### 8.1 نقاط التكلفة الأساسية

1. **مسك القناع على كل إطار** في DrawIn/Erase/MaskRevealable: `mask.clear()` + إعادة بناء geometry كاملة لكل progress. هذا هو الـ hot path الحقيقي.
2. **توليد مسارات المحارف** (استخراج بكسلات + thinning + BFS لجزر) — مكلف جدًا لذا يعتمد على: cache ذاكرة (Promise) + IndexedDB دائم + دقة تقريبية في المفتاح.
3. **النص المتجهي SplitText**: كل محرف SplitText منفصل = draw calls كثيرة؛ التخفيف: bitmap fonts تغلبه.
4. **قنوات الفلاتر**: كل filter = render pass. `AlphaFilter` مع `padding=100` (`consts.ts:3-4`) لأن المحتوى قد يمتد؛ وFXAA على كل عنصر revealable.
5. **كل المشاهد مركّبة دائمًا**: التخفيف هو `visible` لا unmount + `VisibilityManager` يخفي ما خرج.

### 8.2 التخفيفات الموجودة

| التحسين | الملف/السطر | الأثر |
|---|---|---|
| تعطيل التفاعل كليًا على الـ stage | `PixiPlayer.tsx:82-83` | لا hit-testing ولا events على مئات العناصر |
| `autoStart={false}` + `sharedTicker={false}` + render من GSAP | `PixiPlayer.tsx:117-119,43-63` | قرعة واحدة فقط للزمن؛ لا ticker منافس |
| إلغاء القناع في الحالتين الطرفيتين | `DrawIn.tsx:81-98`، `MaskRevealable.tsx:97-111` | العناصر المستقرة لا تدفع ثمن mask |
| `prepare.upload()` قبل العرض | كل مكوّنات التحميل | لا رفع مزامن مفاجئ (jank) أثناء التشغيل |
| FXAA مبني على Luma+Alpha | `filters/FXAAFilter.ts:53-58` | تنظيف حدود القناع المسنّنة بسعر filter واحد، وليس MSAA كامل |

### 8.3 أين تتسرّب الكلفة فعلًا (ملاحظات)

- `useApplySplitTextCharStyles` يعيد بناء style لكل محرف عند كل تغيير في `element.styles` — مقبول لأن التغيير نادر.
- `PositionAndAlphaContainer` ينشئ `AlphaFilter` جديدًا في `useMemo` عند تغيير `element` (لا cache مشترك) — مئات الفلاتر إذا كان العنصر شفافًا فقط.
- `generateBaselineCorrection` ينشئ WebGLRenderer كامل لكل قياس غير مخزّن (مرة لكل تركيبة).
- `howl.seek` يتجاهل إزاحة الـ sprite (تعليق في `AudioPlayerContext.tsx:134`) — يعني seek الجماهيري قد يحتاج حسابًا يدويًا.
- مكتبة الأصوات كلها عبر مؤقتات JS (`setTimeout`) لا عبر ساعة صوتية — عرضة للانحراف إن تجمّد main thread (مثلًا أثناء توليد القناع).

## 9. ما يحتاجه منافس + كيف نبني أفضل

### 9.1 متطلبات الوظيفة (الحد الأدنى للمنافسة)

1. **نموذج زمني حتمي مركزي** كما هنا: timeline واحدة + timeline لكل مشهد/عنصر، مع قفز عشوائي صحيح. أي شيء أقل سيظهر في الإنتاج عند التصدير.
2. **رسم تدريجي حقيقي**: سبليت SVG (strokes/fills/reveal) + الماسكات + مسارات قناع للمحارف، وإلا سيبدو النص كطبقة كاملة مقصوصة — وهو الفرق البصري الأول بين محرّك جيد ومحرّك رخيص.
3. **كاميرا per-scene متعددة الـ keyframes** مع حساب الموضع عند أي زمن، وتعويض المقياس في مسافات الأنيميشن.
4. **نص عربي كامل**: وصل، تشكيل، BiDi، تحكّم في kashida والمسافات.
5. **وجود/غياب جاهزية العناصر** (loading states) بدل وميض.
6. **تصدير حتمي** frame-by-frame بنفس الشجرة، وليس شجرة مختلفة للتصدير (وهو ما يفعله VideoScribe بذكاء: نفس المكوّنات + `seekAndRender`).

### 9.2 نقاط ضعف VideoScribe المرصودة (وهي فرصنا)

| الضعف | الدليل من الكود | فرصتنا |
|---|---|---|

### 9.3 معمارية مقترحة لمنافس

1. **فصل ثلاث طبقات:** (أ) `ProjectModel` (نقي، قابل للتحقق مثبت على JSON schema)، (ب) `Scheduler` يحوّل النموذج إلى جدول زمني (start/end لكل مرحلة، بلا أي رسم)، (ج) `Renderer` (WebGPU/WebGL) يستهلك `(time) → frame state`. GSAP يبقى ممكنًا كطبقة easing فقط، أما الأفضل فهو محرّك time مستقل بمنحنيات مخصصة (cubic-bezier + springs) قابل للتشغيل headless (Node/markup) للتصدير السحابي بدون متصفح بكسل-بكسل.
2. **الرسم بحشمة (brush engine) بدل قناع متجدّد:** ختم (stamp) على texture مسرودة، مع دعم ضغط/سرعة/نعومة، وهو ما يفتح باب «فرش حقيقية» (brush presets) لم يقدّمه VideoScribe.
3. **عربي بالمستوى الأول:** shaping في مكتبة واحدة مشتركة بين المحرّر واللاعب والتصدير، مع اختبارات بصرية snapshot لـ 1000 نص عربي + تشكيل، ودعم RTL/LTR مختلط وأرقام.
4. **تسريع وهندسة تسلسل:** معمارية «scene graph مع أوقات نصف مفتوحة [start,end)» كما يفعل [مذكور في الكود: `RendererCapture.tsx:48-50`] لكن مع زمن افتراضي ونظام أحداث ملتزم بالعقد (events عند بدء/انتهاء كل مرحلة).
5. **إضافات (Plugins):** نقاط تمديد لأنواع عناصر (asset loaders، animations، transitions) على غرار `LoaderParser` في Pixi، مع marketplace؛ VideoScribe مغلق تمامًا هنا.
6. **تشغيل على الخادم:** نفس الـ scheduler لكن renderer بديل (skia-canvas أو WebGPU headless) — ميزة تنافسية واضحة.
7. **الصوت master clock:** `AudioContext.currentTime` مرجعًا، والبصريات تُشتق منه، مع `setTimeout` لا يُستخدم إلا كإشارة تحضيرية.

## 11. ملاحظات وديون تقنية (مرشّحة كأخطاء حقيقية)

## 12. خاتمة

VideoScribe بنى محرّكًا بسيطًا فكريًا وقويًا وظيفيًا: **كل شيء tween على خاصية، وكل tween على timeline واحدة، والزمن كله مدرج من حساب رياضي واحد** (مدد ← أطوال ← تواريخ مطلقة). ما يجعله مناسبًا للتصدير السحابي هو أن نفس الشجرة تُستهلك في المتصفح وفي الرندر، والقدرة الفريدة هي الرسم حرفًا-حرفًا المدفوع بمسارات مستخرجة من البكسلات، مع bitmap fonts مولّدة عند الطلب.

للتغلّب عليه، لا نحتاج «بيكسل أكثر» فقط، بل: **زمن افتراضي حتمي، عربي shaped بالكامل، فرش حقيقية بختم تراكمي بدل قناع متجدد، WebGPU، وساعة صوت**. هذه الخمس قابلة للبناء بفريق أصغر لأن الصعب (المحاذاة مع Fabric، وتعويض عيوب Pixi) لن نحتاجه إذا بنينا استقلالًا عن Pixi أصلًا.
